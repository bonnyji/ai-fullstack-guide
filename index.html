AI辅助一人全栈开发方法

作者：BonnyJi
联系：bonnyji@163.com
© 2026 BonnyJi · 转载请注明作者及原文链接

一个人负责业务定义、架构取舍和验收，借助 AI 完成数据库、前后端、飞书机器人和多端报告开发，通过 GitLab 与 CI/CD 发布，再用 Skill 固化经验、用定时任务承担重复运行。

  • 开发交付： 需求 → 跨仓库开发 → 验证 → GitLab → CI/CD → 部署验收 → 运行维护。
  • 能力复用： 数据接口 → Dashboard、机器人和报告 → Skill 与自动化 → 反馈改进。

名词 含义
管理后台 团队通过浏览器查看经营数据、维护目标和项目的业务系统
前端 用户看到的页面、图表、表单与交互
后端 处理业务规则、数据查询、权限和任务执行的服务
数据库 保存收入、客户、项目、配置及运行记录等数据
Dashboard 通过指标、图表、筛选和明细分析业务的看板
GitLab／GitHub 托管代码、管理版本和协作的平台
CI/CD 按配置执行检查、测试、构建及交付／部署的流水线
飞书机器人 通过飞书消息和卡片与用户交互、连接业务服务的应用入口
NewAPI 统一模型调用入口，供不同 AI 能力共享接入与模型路由
OpenCode 本案例中用于理解问题、加载知识、调用工具和组织回答的 Agent 框架

一、个人如何独立完成开发闭环

个人负责 AI 辅助执行 工程体系提供
业务目标、口径与优先级 理解代码、设计实现、修改前后端 Git 版本和变更记录
架构取舍、权限与边界 编写查询、接口、页面和交互 自动测试、构建与部署
真实业务验收 联调、排障、文档和检查 日志、回滚与任务状态

每次开发按完整功能组织任务。例如“增加月度收入分析”，同时处理：

收入如何计算 → 数据在哪里 → 谁能查看 → 接口如何返回 → 页面如何展示 → 如何验证 → 如何发布。

二、开发前准备

准备项 具体内容
指标口径 收入、目标、预测的计算方式、期间与单位
分析维度 时间、区域、部门、产品、客户
数据权限 谁可以查看、维护、审核和发送
数据来源 表结构、字段映射、关联关系、更新方式
前后端 GitLab 项目 仓库地址、本地目录、分支、依赖和开发规范
AI 环境 NewAPI 接入、模型选择、超时与错误处理
飞书环境 应用、机器人、权限、事件、回调和可用范围
部署环境 CI/CD、服务器、域名、端口、配置、日志和回滚
验收样例 真实输入、预期结果及权限边界

仓库权限前提： 使用团队项目时，需要给独立开发者开放前后端 GitLab 项目的必要权限，包括读取、提交，以及按团队规则执行合并和流水线操作。个人实践可以自行创建 GitHub 前后端仓库，用 GitHub Actions 配置对应流程。

用户体验提升：管理后台提供外网 HTTPS 访问，用户从电脑、手机或飞书卡片链接直接进入后台与报告页，减少网络切换和访问障碍。

统一域名通过反向代理连接内部服务，页面和接口执行登录与数据权限校验。端口清单记录所属服务、用途、调用关系和健康检查方式。

核对外网入口、内部端口与代理关系，

三、Dashboard 与管理后台：从需求文档贯通全栈

开发顺序：

整理需求 → 核对数据 → 开发后端接口 → 开发前端页面 → 权限验证 → 真实数据对账。

先完成“按部门查看月度收入”，再增加同比、完成率、区域贡献、客户排名和明细。需要维护目标、预测和项目进度时，增加数据表、写入接口、表单校验、事务及操作记录。

需求文档明确以下内容：

信息 示例
页面结构 菜单调整、Matrix／Trends、指标卡片、客户排名
复用对象 已有 Dashboard 的布局、图表和交互
数据规则 有效合同条件、金额计算、汇率关联
统计口径 客户去重、订单去重、业务类型分类

AI 结合需求文档、现有代码和数据库完成实现。文档存在歧义时，先核对，再开发。

四、NewAPI：共享模型接入

机器人问答、报告分析、翻译和图片生成，通过 NewAPI 共享接入地址、认证和模型路由。各能力分别配置模型、提示词、超时和输出要求。

能力 分工
经营问答 理解问题、选择工具、解释结果
报告分析 根据真实数据生成分析草稿
翻译 转换语言，保护数字和专有名称
分析制图 先确认数据，再交给对应能力生成

文本和图片等协议由对应适配器处理，分别记录调用失败、数据不足和输出不合规。

Prompt 示例：复用模型接入

复用现有 NewAPI 通道开发报告分析能力。

共享接入地址与认证，单独配置模型、超时和输出要求。
输入保留数据来源，输出区分事实、分析和建议。

分别处理调用失败、数据不足和输出不合规，
避免在不同模块重复维护供应商接入逻辑。

五、飞书机器人：平台配置与代码一起开发

1. 确定机器人能回答的问题

问题类型 示例
指标查询 本月收入是多少？
对比分析 与去年同期相比有什么变化？
维度拆解 各区域贡献多少？
排名明细 收入最高的客户有哪些？
进度查询 哪些项目延期？
综合分析 目标缺口主要在哪里？

2. 配置飞书应用

设置项 主要内容
应用与机器人 创建应用、启用机器人、配置名称和功能说明
权限 按功能申请消息、群、通讯录、图片及文件等权限
可用范围与发布 确认哪些用户和群可以使用，发布应用版本
事件接收 WebSocket 长连接或 HTTP 事件回调
卡片与授权回调 按所用能力配置对应回调方式与地址
凭据与运行 保存配置，处理连接恢复、日志和错误

WebSocket 由服务主动连接飞书接收事件；HTTP 回调需要可达的 HTTPS 地址。消息事件、卡片动作和网页授权分别配置与验证。

飞书应用可用范围与业务数据权限分别校验。

3. 用 OpenCode 收敛问答链路

OpenCode 负责问题理解、知识加载、工具调用与最终回答；Python 服务负责身份、消息、会话和卡片封装。

约束 实现方式
业务知识 数据字典、指标口径、查询示例
数据访问 只读 SQL、表白名单、超时、行数和查询次数限制
数值计算 同比、完成率、贡献等交给确定性工具
回答范围 明确期间、范围和证据；数据不足时说明
回答链路 OpenCode 输出最终回答，Python 不再调用模型改写

六、多端报告：生成、审核与发送

报告流程：

生成分析草稿，定版数据快照 → 人工审核保存 → 手机／飞书／邮件渲染 → 发送归档。

草稿记录数据与来源，定版后绑定快照，审核和发送针对同一版本。

渠道 适配重点
移动页面 阅读布局、筛选、明细、登录与历史查看
飞书卡片 内容大小、图表、分页、按钮与报告链接
HTML 邮件 表格布局、内联样式、图片及客户端兼容

报告按指标、趋势、区域贡献、重点客户和经营分析等模块组织，各渠道选择不同内容组合。

发送记录保存接收对象、渠道、内容版本、实际渲染结果与状态。历史链接读取发送时的内容；结果不确定时先核查，再决定是否重发。

Prompt 示例：开发多端报告

基于现有收入分析开发月度经营报告。

流程：
生成分析草稿，定版数据快照，
人工审核保存后，适配手机、飞书和 HTML 邮件。

各渠道引用相同事实与已保存分析，
支持按渠道选择报告内容。
链接使用外网 HTTPS 地址，适配飞书 WebView，
登录后按权限读取原发送版本。

实现防重复、发送归档和失败处理，
分别验证预览、链接访问及实际送达。

七、Skill：固化标准和偏好

当任务经常重复、标准相对稳定，而且每次都需要解释背景或纠正结果时，适合开发 Skill。

例如生成符合团队管理风格的经营报告：

输入材料 提炼内容
历史报告与优秀样稿 结构、信息取舍、分析深度
文字风格与修改案例 标题、措辞、篇幅、初稿到定稿的变化
图片与图表要求 配色、版式、图表选择、标注与单位
管理风格 关注点、风险表达、建议的具体程度
业务口径与禁用规则 数字使用、证据要求、应避免的表述

开发过程：

输入材料 → 提炼规则 → 使用新材料试生成 → 人工反馈 → 修订验证 → 固化 Skill。

Skill 写清触发条件、输入、工具、执行步骤、输出和验证方法。样稿作为参考，稳定操作配套脚本；本期数据和具体业务判断每次输入。

数据分析、飞书配置检查、部署验收和排障也可按此方式整理。

Prompt 示例：开发报告 Skill

根据历史报告、定稿修改记录和视觉样例，
开发“团队经营报告”Skill。

提炼结构、文字风格、图表要求和管理关注点。
总结保留什么、删去什么、风险如何表达、
建议具体到什么程度，以及应避免的写法。

将表达规则与历史业务事实分开。
使用新材料试生成，根据我的反馈修订，
验证后固化为 Skill，保留典型样例和检查步骤。

八、定时任务：持续执行已有流程

设计项 内容
触发 时间、时区、统计期间和范围
就绪条件 数据是否完整、是否已审核
执行控制 状态、超时、有限重试、防重复
反馈 日志及完成、失败、需人工处理时的通知

应用内任务由调度器调用已有代码或接口；需要 AI 的步骤，由能加载相应 Skill 的执行环境完成。

Prompt 示例：定时报告

将现有月报流程接入定时任务。

明确北京时间、统计月份、部门范围、
数据就绪条件和审核要求。
数据未就绪时等待，未经审核不得发送。

复用已有流程，实现状态、超时、有限重试、
防重复和执行日志。
完成、失败或需人工处理时通知。
先模拟验证，再按授权验证真实交付。

九、GitLab 与 CI/CD：完成部署交付

本地开发与验证 → 分别提交 GitLab → CI/CD 测试构建部署 → 平台配置发布 → 线上业务验收 → 回滚准备与资源清理。

一次需求同时记录前端、后端、数据库和飞书配置变更：

  1. 前后端分别提交，记录版本与数据库变更的对应关系。
  2. 跟踪流水线，失败后定位、修复并重新验证。
  3. 核对数据库迁移，先发布兼容后端，再发布前端。
  4. 完成飞书应用配置与版本发布。
  5. 验收外网访问、登录、数据、权限、机器人交互、报告链接和实际送达。
  6. 保留回滚版本，检查日志、磁盘和文件存储，清理本次无用资源。

部署成功、接口响应、文件上传成功和消息送达分别验证。

共享服务器只清理已确认属于本项目、已停止且无后续用途的临时资源。新版本健康后，保留当前版本和至少一个已验证回滚版本，再清理多余产物。不删除业务文件、数据库、数据卷或挂载目录；构建缓存按归属、年龄和容量限制回收，不执行无范围清理。

Prompt 示例：完成交付

完成本次功能的前后端交付。

检查变更并执行必要验证，
分别提交 GitLab，跟踪 CI/CD 直到结果明确。
核对数据库迁移、环境配置和飞书平台配置。

上线后验证真实业务路径与多端结果。
记录前后端版本、数据库与配置变更、
回滚点和未验证事项。

健康检查通过后，清理本项目本次无用临时资源，
保留已验证回滚版本，记录磁盘与文件存储状态。

十、运行反馈与下一轮开发

使用问题进入下一轮需求，已验证的标准和操作写入 Skill，重复流程交给定时任务。

每次交付留下四类记录：

记录 内容
代码版本 前后端提交、数据库迁移与配置变更
发布结果 测试、构建、部署和飞书应用版本
业务验收 访问、数据、权限、交互与实际交付结果
运行保障 日志、回滚版本、资源清理和待处理事项
